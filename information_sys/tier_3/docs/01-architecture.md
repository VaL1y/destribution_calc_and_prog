# Архитектура и ответственность компонентов

## PostgreSQL

PostgreSQL отвечает за данные:

- primary принимает чтение и запись;
- standby принимает чтение и применяет WAL;
- `pg_basebackup` создаёт начальную копию standby;
- `pg_promote()` превращает конкретную standby в primary.

PostgreSQL не выбирает лидера автоматически. Это не отключённая нами функция,
а сознательная граница продукта: один узел не способен достоверно отличить
падение соседа от сетевого разделения и не должен самовольно создавать второй
primary.

## repmgr и repmgrd

`repmgr` — административная команда: зарегистрировать узел, показать кластер,
сделать switchover, присоединить бывший primary.

`repmgrd` — постоянно работающий демон. Он:

1. наблюдает за локальной PostgreSQL и её upstream;
2. несколько раз перепроверяет отказ;
3. участвует в выборе кандидата среди standby;
4. вызывает promotion;
5. переводит остальные standby на нового primary.

В Compose эти процессы уже находятся внутри каждого контейнера. Основные
параметры:

| Параметр | Значение |
|---|---|
| `REPMGR_PARTNER_NODES` | адреса всех трёх участников |
| `REPMGR_PRIMARY_HOST` | только начальный primary при первом запуске |
| `REPMGR_NODE_ID/NAME` | постоянная идентичность ноды |
| `REPMGR_NODE_PRIORITY` | предпочтение при выборе кандидата |
| `REPMGR_RECONNECT_*` | сколько раз проверять отказ перед реакцией |

Приоритеты `300`, `200`, `100` означают: после отказа `pg-1` предпочтительнее
повысить `pg-2`; если весь условный удалённый сервер исчез, остаётся `pg-3`.

## Почему это не строгий кворум

Количество PostgreSQL-ноды само по себе не создаёт consensus. В repmgr есть
обмен наблюдениями и выбор кандидата, но нет отдельного линейризуемого leader
lock, которым владеет ровно одна сторона сетевого разделения.

Если `pg-1` и `pg-2` действительно выключились, `pg-3` должна повыситься.
Но для `pg-3` точно так же выглядит разрыв сети:

```text
вариант A: pg-1 и pg-2 выключены
вариант B: pg-1 и pg-2 работают, но недоступны для pg-3
```

Разрешив promotion в A, без третьей независимой точки мы разрешаем его и в B.
Это выбранный нами компромисс доступности, а не ошибка настройки.

## Асинхронная репликация

`POSTGRESQL_NUM_SYNCHRONOUS_REPLICAS=0` означает, что COMMIT на primary не ждёт
подтверждения standby. Поэтому:

- обычная запись быстрее и не зависит от WAN RTT;
- standby может отставать;
- подтверждённые primary транзакции могут отсутствовать после аварийного
  promotion;
- «задержка несколько секунд» является наблюдаемой целью, а не гарантией.

Будем измерять три позиции WAL: отправленную primary, полученную standby и
применённую standby.

## Подключение FastAPI

Дополнительный proxy пока не нужен. libpq/psycopg умеет получить несколько
адресов и выбрать сервер по `target_session_attrs`.

В `api/db.py` созданы два пула:

- `read-write` перебирает адреса, пока не найдёт текущий primary;
- `prefer-standby` предпочитает read-only standby и использует primary только
  если standby недоступны.

Основной `engine` направлен на primary: его используют транзакции изменения и
`/api/status`. При сборке образа helper `read_connection()` переключается на
`read_engine`; через него работают списки товаров, категорий и движений. Так мы
меняем только инфраструктурную точку подключения, не дублируя складскую логику.

После failover уже открытые соединения могут получить ошибку. Новые соединения
снова переберут список хостов и найдут новый primary. Это поведение также нужно
измерить, а не маскировать бесконечными повторными попытками.

## Два приложения для опыта split-brain

`api-remote` использует только `pg-1,pg-2` и доступен на порту `8000`.
`api-local` использует только `pg-3` и доступен на порту `8001`. Второй API
включён в профиль `splitbrain`, поэтому при обычном запуске он не создаётся.

Для согласования используется отдельный append-only журнал:

```text
inventory_events(event_id UUID, source_node, product_id, delta, created_at)
```

Разрешены только положительные `delta`. Поэтому слияние не требует решать,
какое из двух значений остатка «последнее»: мы объединяем множества уникальных
событий, а повторный UUID безопасно пропускаем.
