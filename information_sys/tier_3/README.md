# Tier 3: PostgreSQL streaming replication и автоматический failover

Этот каталог — следующий учебный слой после `tier_2`. Складской FastAPI и его
SQL-схема переиспользуются без копирования, а одна PostgreSQL заменяется
кластером из трёх экземпляров.

Стенд подготовлен, но ещё не запускался. Это намеренно: поднимать компоненты и
проверять каждую стадию нужно последовательно по инструкции.

## Что строим

```text
                  api-remote / api-local
                reads /           \ writes
                      /             \
        prefer-standby               read-write
                    /                 \
    +---------------------------------------------+
    | условный удалённый сервер                   |
    | pg-1: initial primary   pg-2: standby       |
    | repmgrd                  repmgrd             |
    +-----------------------+---------------------+
                            | streaming WAL
    +-----------------------+---------------------+
    | условный локальный сервер                   |
    | pg-3: standby + repmgrd                     |
    +---------------------------------------------+
```

Сначала всё запускается на одной машине в одной Docker-сети. После того как
поведение станет понятным, `pg-1` и `pg-2` переносятся на удалённый сервер, а
`pg-3` — на локальный.

## Почему здесь repmgr, а не Patroni

PostgreSQL умеет передавать и применять WAL, работать standby и выполнять
локальную команду promotion. Но в PostgreSQL нет встроенного распределённого
алгоритма выбора нового primary.

`repmgrd` — наблюдатель возле каждой PostgreSQL. Он проверяет upstream,
выбирает подходящую standby, выполняет promotion и заставляет остальные узлы
следовать за новым primary. Его метаданные хранятся в самом PostgreSQL, поэтому
для первого стенда не нужен отдельный etcd.

Это проще, но имеет осознанное ограничение: без независимого арбитра невозможно
надёжно отличить падение удалённого сервера от разрыва сети до него. Мы
разрешаем локальной ноде повыситься, поэтому при сетевом разделении потенциально
возможен split-brain. Это не скрытая ошибка стенда, а один из главных опытов.

Подробности: [архитектура и роли](docs/01-architecture.md).

## Подготовленные файлы

- `docker-compose.yml` — три PostgreSQL/repmgr, два FastAPI и необязательный Locust;
- `.env.example` — пароли и ограничения ресурсов;
- `api/Dockerfile` — собирает существующий API из `tier_2`;
- `api/db.py` — создаёт отдельные пулы для primary и standby;
- `api/tier3_main.py` — добавляет append-only события для опыта split-brain;
- `scripts/reconcile_events.py` — переносит недостающие события в выбранный primary;
- `docs/02-lab-steps.md` — запуск маленькими проверяемыми шагами;
- `docs/03-two-hosts.md` — что позже переносить на каждую машину;
- `docs/04-coordinators.md` — Patroni, etcd, Consul и ZooKeeper без смешения ролей.

## Важное ограничение образа

Для первого локального опыта зафиксирован свободно доступный образ
`bitnamilegacy/postgresql-repmgr:17.6.0-debian-12-r2`. Он удобен тем, что явно
показывает параметры repmgr, но больше не получает обновлений. Его нельзя
выставлять в Интернет и нельзя считать production-решением. Перед переносом на
реальные серверы мы заменим его собственным образом из поддерживаемых пакетов
PostgreSQL/repmgr либо установим пакеты непосредственно на серверы.

## Первый шаг

Не выполняйте сразу `docker compose up -d`. Начните с раздела «Шаг 0» в
[пошаговой лабораторной работе](docs/02-lab-steps.md). Там каждая нода
поднимается отдельно и после каждого действия проверяется её роль.

## Упрощённое согласование после split-brain

Мы не объединяем произвольные состояния таблиц. Оба приложения только добавляют
события прихода в `warehouse.inventory_events`. У события глобальный UUID,
поэтому после восстановления связи можно выбрать один primary и скопировать в
него отсутствующие события через `ON CONFLICT DO NOTHING`. Затем проигравшая
ветка пересоздаётся как standby.

Это сохраняет обе независимые записи, но остаётся намеренно узкой моделью:
события нельзя изменять или удалять, а `delta` пока может быть только
положительной.
