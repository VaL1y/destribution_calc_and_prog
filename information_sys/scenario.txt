Для учебного восстановления применяется политика winner-takes-all: ветка pg-1 + pg-3 остается источником истины, а pg-2 возвращается как standby через pg_rewind или повторное клонирование. События, записанные только в проигравший pg-2 после разделения, теряются. Хорошо, мы посмотрели почему сплитбрейн это плохо. Как с этим бороться?
В этом нам помогает "кворум". По сути это система голосования, которая помогает определить, какая часть распределенной системы имеет право сохранить или выбрать primary.
Реализовать согласованное голосование нам поможет ZooKeeper: он хранит небольшое состояние кластера и лидерскую блокировку, но складские данные в нем не находятся.
etcd является альтернативным DCS с похожей ролью; здесь используется ZooKeeper, чтобы отдельно рассмотреть его ансамбль и правило большинства.
И так, теперь рядом с каждой PostgreSQL-нодой у нас будет находиться Patroni — процесс, который запускает и контролирует PostgreSQL, проверяет лидерскую блокировку в DCS, выполняет promotion и возвращает старый primary как replica.
ZooKeeper располагается независимо: один голос в первом ЦОД, один во втором и третий голос на отдельной witness-площадке.
*показываю компоуз tier-4: compose.remote.yml, compose.local.yml и compose.witness.yml
В первом ЦОД находятся pg-1, pg-2 и ZooKeeper-1, во втором — pg-3 и ZooKeeper-2, а на третьей площадке только ZooKeeper-3. Для решения нужны два голоса из трех, поэтому отказ любого одного ЦОД оставляет quorum, а изолированная площадка с одним голосом не может создать второй primary. В Patroni обязательны имя кластера и ноды, адреса PostgreSQL и REST API, каталог данных, учетные данные репликации и список DCS; ttl, loop_wait, retry_timeout, maximum_lag_on_failover и use_pg_rewind задают выбранную политику и скорость failover.
```cmd
docker network disconnect warehouse-tier3-net warehouse-postgres-service-api-1
docker network disconnect warehouse-tier3-net warehouse-local-api-1
docker network disconnect warehouse-tier3-local-branch warehouse-local-api-1
docker compose -f tier_3\compose.yml down

REM Проверяем три Compose-файла с единым tier_4\.env.
docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml config --quiet
docker compose --env-file tier_4\.env -f tier_4\compose.local.yml config --quiet
docker compose --env-file tier_4\.env -f tier_4\compose.witness.yml config --quiet

REM Сначала запускаем все три голоса ZooKeeper. Поодиночке они не образуют quorum.
docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml up -d zk-1
docker compose --env-file tier_4\.env -f tier_4\compose.local.yml up -d zk-2
docker compose --env-file tier_4\.env -f tier_4\compose.witness.yml up -d zk-3
timeout /t 20 /nobreak

docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml ps
docker compose --env-file tier_4\.env -f tier_4\compose.local.yml ps
docker compose --env-file tier_4\.env -f tier_4\compose.witness.yml ps

REM Только после появления ZooKeeper quorum запускаем Patroni/PostgreSQL.
docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml up -d --build pg-1 pg-2
docker compose --env-file tier_4\.env -f tier_4\compose.local.yml up -d --build pg-3

docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml exec pg-1 patronictl -c /etc/patroni/patroni.yml list

docker network create warehouse-tier4-app
docker network connect warehouse-tier4-app warehouse-postgres-service-api-1
docker network connect warehouse-tier4-app warehouse-local-api-1
docker network connect --alias pg-1 warehouse-tier4-app warehouse-tier4-remote-pg-1-1
docker network connect --alias pg-2 warehouse-tier4-app warehouse-tier4-remote-pg-2-1
docker network connect --alias pg-3 warehouse-tier4-app warehouse-tier4-local-pg-3-1
docker compose -f service\compose.yml exec api python scripts/migrate.py
curl http://127.0.0.1:8000/api/status

На одной машине мы имитируем потерю площадок остановкой их контейнеров; настоящее направленное разделение сети позже выполняется firewall или отключением межсерверного VPN.
Сначала имитируем полный отказ первого ЦОД: во втором ЦОД и на witness остаются два голоса, поэтому pg-3 может автоматически стать Leader.

curl http://127.0.0.1:8001/api/status
```
Возвращаем первый ЦОД; его PostgreSQL-ноды должны присоединиться к pg-3 как replica, а не стать вторым primary.
```cmd
docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml start zk-1

docker compose --env-file tier_4\.env -f tier_4\compose.remote.yml start pg-1 pg-2

```
Теперь проверяем защиту от split brain: выключаем witness и еще один голос, после чего остается 1/3 и Patroni должен остановить запись, а не создать новый primary.
```cmd

```

Для реальной системы полезно отдельно замерить RTO от падения Leader до первой успешной записи, RPO по последней подтвержденной складской операции, задержку WAL на удаленной replica, маршрутизацию чтения через /api/demo/read-node, возврат старого primary, поведение при отказе witness и восстановление из backup/PITR, потому что реплика не защищает от ошибочного удаления или логической порчи данных.
