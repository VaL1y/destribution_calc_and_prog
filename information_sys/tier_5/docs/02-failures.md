# Опыты с отказами tier_5

Сценарии намеренно совпадают с `tier_4`, чтобы сравнивать etcd и ZooKeeper при
одинаковом PostgreSQL/Patroni.

## Реплика PostgreSQL

Остановите ноду, которая указана как `Replica`, продолжите записи, затем верните
её и измерьте время догоняния WAL:

```bash
docker compose --env-file .env -f compose.remote.yml stop pg-2
docker compose --env-file .env -f compose.remote.yml start pg-2
docker compose --env-file .env -f compose.remote.yml logs -f pg-2
```

## Текущий primary

Найдите Leader через `patronictl list` и остановите именно его. Измерьте RTO до
первой успешной записи и проверьте RPO. `maximum_lag_on_failover=1 MiB` не даёт
Patroni выбрать заметно отставшую реплику. После возврата старая primary-нода
должна присоединиться как Replica.

## Один участник ZooKeeper

Остановите любой один `zk-*`. Оставшиеся два голоса сохраняют кворум. PostgreSQL
не должен выполнять failover только из-за потери одного голоса DCS.

## Разрыв сети между серверами

Отключите именно межсерверную сеть/VPN:

- ZooKeeper-1 + ZooKeeper-2 составляют 2/3 на удалённой стороне;
- ZooKeeper-3 один не имеет кворума;
- удалённый PostgreSQL Leader продолжает работу;
- локальный pg-3 не получает право стать primary.

После восстановления сети локальная реплика догоняет WAL. Две истории записей не
возникают и сливать их не требуется.

## Весь удалённый сервер

Ожидаемо пропадут FastAPI, две PostgreSQL-ноды и два голоса ZooKeeper. Оставшиеся
pg-3 + ZooKeeper-3 не имеют кворума, поэтому автоматического promotion не будет.
Это демонстрирует недостаток размещения 2+1 для отказа целой площадки.

Не удаляйте volumes и не применяйте ручной promotion в этих опытах. `down -v` —
не имитация сбоя, а удаление данных.
