# Результаты нагрузочного тестирования

Дата прогона: 17 сентября 2026 года.

Конфигурация:

- PostgreSQL: `0.5 CPU`, `256 MB`, `shared_buffers=64MB`, `max_connections=20`;
- SQLAlchemy: основной пул 5 соединений, 2 дополнительных;
- FastAPI/Uvicorn: один контейнер без ограничения CPU;
- Locust 2.46.3 запускался отдельным контейнером.

## Результаты

| Сценарий | Пользователи | RPS | Среднее | p95 | Ошибки |
|---|---:|---:|---:|---:|---:|
| Чтение, маленький журнал | 10 | 74.5 | 7.8 мс | 16 мс | 0% |

## Найденные узкие места

### 1. API ограничивает чтение на маленьких данных

При переходе от 50 к 100 пользователям пропускная способность выросла только с 267 до 288 RPS, а средняя задержка — с 55 до 207 мс. FastAPI потреблял около двух CPU, PostgreSQL — только 20–30% одного CPU. Значит, на маленьком наборе данных первой достигает насыщения связка FastAPI, синхронных обработчиков и пула SQLAlchemy, а не PostgreSQL.

`max_connections=20` пока не является ограничением: API допускает максимум 7 одновременных соединений из одного процесса.

### 2. Запрос журнала не использует подходящий индекс

Экран последних операций выполняет:

```sql
ORDER BY m.created_at DESC, m.id DESC
LIMIT 20
```

Существующий индекс начинается с `product_id`, поэтому он не подходит для глобального списка операций. На 7 820 строках `EXPLAIN ANALYZE` показал `Seq Scan`, соединение всех строк и `top-N heapsort`.

После роста журнала PostgreSQL достигла лимита `0.5 CPU`: Docker показывал 47–50% CPU. В одинаковом тесте на 50 пользователей:

- RPS снизился с 267 до 201;
- среднее время выросло с 55 до 114 мс;
- p95 вырос со 110 до 260 мс.

Первый кандидат на следующий эксперимент:

```sql
CREATE INDEX stock_movements_created_idx
ON warehouse.stock_movements (created_at DESC, id DESC);
```

После добавления индекса нужно повторить `read-50-after-writes` и сравнить план и CSV.

### 3. Один товар становится горячей строкой

`SELECT ... FOR UPDATE` правильно защищает остаток от потерянных обновлений, но все операции одного товара выполняются последовательно. При 30 конкурентных пользователях PostgreSQL показывала одновременно:

- `Lock:tuple` — 3–5 сессий;
- `Lock:transactionid` — 1–2 сессии;
- `IO:WALSync` — 1 сессию.

Рост с 5 до 20 пользователей дал лишь 36% дополнительной пропускной способности, но увеличил среднюю задержку примерно в пять раз. Это ожидаемая цена строгой консистентности одной складской позиции.

## Порядок дальнейших экспериментов

1. Добавить индекс журнала и повторить тест чтения на выросшей таблице.
2. Только после исправления запроса сравнить размеры пула SQLAlchemy `5+2`, `10+5` и несколько Uvicorn workers.
3. Проверить записи по разным товарам, чтобы отделить общую скорость записи от блокировки одной строки.
4. Установить критерий, например: `p95 < 200 мс`, ошибок меньше `1%`, и искать максимальный устойчивый RPS по этому критерию.

## Сравнение FastAPI workers

Одинаковый сценарий чтения выполнялся со 100 пользователями по 15 секунд. Таблица была очищена от массовых тестовых движений.

| Workers | RPS | Среднее | p95 | p99 | Ошибки |
|---:|---:|---:|---:|---:|---:|
| 1 | 256.2 | 246 мс | 390 мс | 500 мс | 0% |
| 2 | 219.8 | 300 мс | 660 мс | 850 мс | 0% |
| 4 | 166.7 | 444 мс | 830 мс | 1 100 мс | около 22% |

Дополнительные workers не улучшили этот сервис. Обработчики API объявлены как синхронные `def`, поэтому FastAPI уже выполняет несколько запросов одного worker в thread pool. Несколько процессов добавили накладные расходы и создали отдельный SQLAlchemy pool в каждом процессе.

При четырёх workers PostgreSQL начала возвращать `FATAL: sorry, too many clients already`. Текущая верхняя граница подключений:

```text
4 workers × (pool_size 5 + max_overflow 2) = 28
PostgreSQL max_connections = 20
```

Поэтому количество workers, размеры пулов и `max_connections` должны настраиваться вместе. Безопасное приближение:

```text
workers × (pool_size + max_overflow) + служебный резерв <= max_connections
```

При лимите 20 для четырёх workers разумно сначала проверить пул `3+1` на worker, оставив около четырёх соединений PostgreSQL для администрирования и фоновых процессов. После этого тест нужно повторить; сам по себе рост числа workers не гарантирует рост RPS.

## Итоговая конфигурация tier_2: одна PostgreSQL

Конфигурация после эксперимента с workers:

- 2 Uvicorn workers;
- SQLAlchemy pool `12+3` в каждом worker;
- не более 30 прикладных соединений;
- PostgreSQL `max_connections=40`;
- PostgreSQL `0.5 CPU`, `256 MB`, `shared_buffers=64 MB`;
- Uvicorn access-log отключён на время benchmark;
- API и PostgreSQL находятся в одной локальной Docker-сети.

Перед каждой точкой benchmark удаляет только товары с SKU `LOAD-%`, выполняет `VACUUM ANALYZE`, пересоздаёт API и ждёт healthcheck. Запись распределяется по 32 товарам, поэтому результат не ограничен одной горячей строкой.

### Контрольные результаты

| Сценарий | Пользователи | RPS | Среднее | p95 | Ошибки |
|---|---:|---:|---:|---:|---:|
| Чтение, рабочая точка | 50 | 340.8 | 18 мс | 51 мс | 0% |
| Чтение, насыщение | 200 | 524.1 | 236 мс | 350 мс | 0% |
| Чтение, перегрузка | 400 | 487.6 | 643 мс | 910 мс | 0% |
| Запись, рабочая точка | 20 | 355.6 | 34 мс | 78 мс | 0% |
| Запись, насыщение | 80 | 342.2 | 206 мс | 360 мс | 0% |
| Запись, перегрузка | 160 | 343.6 | 420 мс | 680 мс | 0% |

При насыщении PostgreSQL использовала 47–50% CPU по `docker stats`, то есть достигала заданного лимита `0.5 CPU`. Память БД оставалась примерно в диапазоне 67–79 MB. Под нагрузкой использовались все 30 прикладных соединений; вместе с измерительным подключением наблюдалось 31 соединение. Ошибок `too many clients` не было.

Практический вывод для этой конфигурации:

- низколатентное чтение: примерно **340 RPS** при `p95 ≈ 51 мс`;
- низколатентная запись по разным товарам: примерно **355 RPS** при `p95 ≈ 78 мс`;
- максимальная пропускная способность чтения: около **500 RPS**, но `p95` уже 350–900 мс;
- запись насыщается около **340–355 RPS**: дополнительные пользователи увеличивают очередь, а не throughput.

Это предел всей связки `FastAPI → SQLAlchemy → PostgreSQL` для заданных запросов и ресурсов, а не универсальная производительность PostgreSQL. Локальная Docker-сеть почти не добавляет сетевой задержки. Эти CSV нужно сохранить как baseline для сравнения со следующим уровнем, где PostgreSQL будет находиться на отдельном сервере.
