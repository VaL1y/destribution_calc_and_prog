# Split-brain и учебное согласование событий

1. Поднимите кластер и выполните миграции по `02-lab-steps.md`.
2. Запустите второй экземпляр сервиса в локальной ветке:

```cmd
cd ../service
set "API_PORT=8001"
set "APP_NODE=local"
docker compose -p warehouse-local up -d --build api
docker network connect warehouse-tier3-local-branch warehouse-local-api-1
```

Подключите второй API к общей сети до начала опыта:

```cmd
docker network connect warehouse-tier3-net warehouse-local-api-1
```

3. Изолируйте `pg-3` и второй API от основной сети, оставив их вместе в
   `warehouse-tier3-local-branch`, затем повысьте `pg-3` только для учебного
   опыта и запишите разные данные через порты 8000 и 8001.
4. Верните оба контейнера в общую сеть. Физические timelines не объединяются:
   текущий легитимный primary остаётся победителем, а записи проигравшей ветки
   намеренно теряются.
5. Перезапустите проигравшую PostgreSQL-ноду. Образ опрашивает доступные partner
   nodes и, благодаря `REPMGR_USE_PGREWIND=yes`, пытается вернуть её к текущему
   primary через `pg_rewind`; если rewind невозможен, выполняется полное
   клонирование. После этого нода входит в кластер как standby.

Если `pg-1` и `pg-2` действительно отказали, а `pg-3` был повышен и продолжал
принимать запись, победителем является `pg-3`. Восстановившийся `pg-1` должен
быть перезапущен уже при доступном `pg-3`, чтобы присоединиться к его актуальной
timeline. Имя ноды не определяет победителя.
