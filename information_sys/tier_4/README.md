# Tier 4 — PostgreSQL + Patroni + etcd

Учебный отказоустойчивый кластер склада на двух физических серверах.

## Размещение

```text
Удалённый сервер                         Локальный сервер
┌──────────────────────────────┐         ┌────────────────────┐
│ FastAPI                      │         │ pg-3 + Patroni     │
│ pg-1 + Patroni               │◄───────►│ etcd-3 (голос 3)   │
│ pg-2 + Patroni               │  VPN/LAN└────────────────────┘
│ etcd-1, etcd-2 (голоса 1, 2) │
└──────────────────────────────┘

Обычная рабочая машина: ничего не запущено.
```

PostgreSQL хранит данные и передаёт WAL репликам. Patroni запускает PostgreSQL,
следит за его ролью, держит лидерский ключ в etcd и выполняет promotion/demotion.
etcd хранит только состояние управления кластером и принимает решение кворумом
2 из 3; пользовательских данных склада в etcd нет.

FastAPI подключается сразу к трём адресам. Для записи libpq ищет `read-write`
узел, для чтения — `prefer-standby`. Отдельный HAProxy в этом уровне не нужен.

## Гарантии стенда

- отказ одного процесса PostgreSQL: Patroni может повысить актуальную реплику;
- отказ одной реплики: primary продолжает работать, вернувшаяся реплика догоняет WAL;
- разрыв между серверами: удалённая сторона имеет 2/3 голосов и остаётся рабочей,
  локальная сторона с 1/3 не становится primary;
- асинхронная репликация: подтверждённая запись теоретически может потеряться,
  если primary погиб до отправки WAL;
- полная потеря удалённого физического сервера **не переживается автоматически**:
  вместе с FastAPI пропадают два голоса etcd, а pg-3 не имеет кворума для promotion.

Последний пункт — сознательное следствие выбранного размещения, а не ошибка
Patroni. Чтобы переживать потерю целого удалённого сервера, три голоса должны
находиться в трёх независимых местах, а приложению нужен второй экземпляр/маршрут.
