# Опыты с отказами tier_4

Перед каждым опытом убедитесь, что `patronictl ... list` показывает один Leader,
две Replica и небольшой `Lag in MB`. Выполняйте только один отказ за раз.

## 1. Перезапуск реплики

Если `pg-2` — Replica, на удалённом сервере:

```bash
docker compose --env-file .env -f compose.remote.yml stop pg-2
# Сделайте несколько приходов через UI.
docker compose --env-file .env -f compose.remote.yml start pg-2
docker compose --env-file .env -f compose.remote.yml logs -f pg-2
```

Наблюдаем: сервис продолжал писать; вернувшаяся реплика получила отсутствующий
WAL. Замерьте время от `start` до состояния `Replica` с нулевым/малым lag.

## 2. Отказ текущего primary

Сначала определите Leader через `patronictl list`, затем остановите именно его,
например:

```bash
docker compose --env-file .env -f compose.remote.yml stop pg-1
```

Повторяйте запрос состояния API и фиксируйте время до успешной новой записи.
Patroni выберет наиболее подходящую доступную реплику, если её отставание не
превышает `maximum_lag_on_failover=1 MiB`. Незавершённый запрос получит ошибку,
а следующий после переподключения пула должен найти новый `read-write` узел.

Верните ноду:

```bash
docker compose --env-file .env -f compose.remote.yml start pg-1
```

`pg_rewind`/повторное присоединение должны вернуть старый primary как Replica.
В асинхронном режиме сравните последнюю подтверждённую операцию до сбоя с данными
после failover: это практическое измерение RPO.

## 3. Обрыв связи между серверами

Временно отключите VPN/маршрут между физическими серверами. Не останавливайте
отдельные Docker-контейнеры: цель — именно сетевое разделение.

- удалённая сторона видит etcd-1 + etcd-2, то есть 2/3, и сохраняет Leader;
- локальная сторона видит только etcd-3, поэтому pg-3 не повышается;
- split-brain и две независимые записи не возникают.

После восстановления связи pg-3 догонит WAL. Согласовывать две версии данных не
нужно, потому что сторона без кворума не имела права стать primary.

## 4. Отказ одного голоса etcd

Остановите `etcd-1` или `etcd-3`. Два оставшихся голоса сохраняют кворум, поэтому
PostgreSQL-роли не меняются. Верните контейнер и проверьте `endpoint status`.

## 5. Потеря всего удалённого сервера

Ожидаемый результат этого конкретного размещения: FastAPI исчезает, pg-3 остаётся
Replica и не повышается, потому что доступен только один голос из трёх. Не
превращайте pg-3 в primary вручную в рамках этого опыта — это обход защиты от
split-brain. Такой результат показывает, почему «три процесса» и «три независимых
зоны отказа» — не одно и то же.

## Что измерять

- RTO: от последнего успешного запроса до первой успешной записи после failover;
- RPO: сколько подтверждённых операций отсутствует после failover;
- время возврата Replica и её максимальный lag;
- ошибки/таймауты API во время переключения;
- нагрузку на primary и две читающие реплики.

Не используйте `docker compose down -v` для обычного сбоя: `-v` удалит данные.
